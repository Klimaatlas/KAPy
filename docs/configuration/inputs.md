# KAPy input configuration

*The configuration of inputs in KAPy is set through a tab-separated table, with one row per input variable. The available configuration options are described here. All options are required.*

## Properties

- <a id="properties/id"></a>**`id`** *(string, required)*: A unique id for this processing group. Cannot contain a space. Must match pattern: `^[^ ]+$` ([Test](https://regexr.com/?expression=%5E%5B%5E%20%5D%2B%24)). Items must be unique.
- <a id="properties/enabled"></a>**`enabled`** *(string or null, required)*: Determines whether the row be used in the workflow. A non-empty value indicates not to use that row.
- <a id="properties/datasetCode"></a>**`datasetCode`** *(string, required)*: A code for the dataset e.g CORDEX, ERA5. Need not be unique. Is used to group related variables from the same data source together further in the analysis (e.g. tas and pr from ERA5). Must not contain a space. Must match pattern: `^[^ ]+$` ([Test](https://regexr.com/?expression=%5E%5B%5E%20%5D%2B%24)).
- <a id="properties/varCode"></a>**`varCode`** *(string, required)*: A code of the variable contained in this dataset. While there is no enforcement of naming conventions in KAPy, the variable names should anyway be standardised across the entire configuration and across input datasets. For example, both ERA5 and CORDEX provide surface temperature, but with different internal variable names in the input files - to ensure that they can be matched together, they should both be assigned the varCode `tas`. Must not contain a space. Must match pattern: `^[^ ]+$` ([Test](https://regexr.com/?expression=%5E%5B%5E%20%5D%2B%24)).
- <a id="properties/units"></a>**`units`** *(string or null, required)*: The units that the input variable is to be converted to for further processing. KAPy takes an active approach to units, requiring them to be declared and consistent throughout the configuration process. Three scenarios are possible 1. If the input dataset does not have units defined, a units attribute will be created and set to this value - in this case, this argument must be defined and will throw an error if undefined.  2. If the input dataset has units, but this argument is empty, the units will be unchanged. 3. If the input dataset has units that are not the same as the specified argument, the input dataset will be converted to the new units using `xclim.core.units.convert_units_to()` - if this function fails, KAPy will also fail. Checks are also applied to ensure that the units are consistent across variables e.g. that all `tasmax` variables have the same units. For more information, see the xclim documentation regarding unit handling https://xclim.readthedocs.io/en/stable/notebooks/units.html.
- <a id="properties/gridCode"></a>**`gridCode`** *(string, required)*: Identifier for the grid that the data set is on. The identifier need not be unique, and most commonly will be duplicated across multiple input sources. Must not contain a space. Must match pattern: `^[^ ]+$` ([Test](https://regexr.com/?expression=%5E%5B%5E%20%5D%2B%24)).
- <a id="properties/path"></a>**`path`** *(string, required)*: Specification of the input files. Four cases are considered. 1. A string describing  a path using glob-matching (e.g. `./resources/CORDEX/tas_*`) can be used to specify multiples files. 2. A path to a single netcdf file. 3. A path to a text file containing a list of input files, one file per line. 4. A path to a text file containing outputs from the md5sum command in unix, consisting of an md5 checksum followed by the file path, one file per line. Note that all paths need to be specified either relative to the working directory, or as absolute paths in the filesystem. See also the tutorials for more information and examples on how this can work, and a discussion of the merits of each approach.
- <a id="properties/internalVarName"></a>**`internalVarName`** *(string, required)*: The internal variable name used within the input file for the variable of interest. For example, in ERA5 files the internal variable name for surface temperature is `t2m` whereas in CORDEX is is `tas`.
- <a id="properties/importScriptPath"></a>**`importScriptPath`** *(string or null, required)*: Path to the custom import script. Use this option to enable useage of a custom script to import data before being written to disk as primVars. If empty, then the default import system in KAPy will be used. Default: `null`.
- <a id="properties/importScriptFunction"></a>**`importScriptFunction`** *(string or null, required)*: Function in the custom import script to be used. Must be supplied if `importScriptPath` is present. Default: `null`.
- <a id="properties/rechunkingStrategy"></a>**`rechunkingStrategy`** *(string, required)*: Determine the approach to rechunking to be employed for this input. The concept of chunking relates to the way that data is stored on disk, and is particularly relevant when dealing with multi-dimensional datasets, such as is common in working with climate data. For example, many functions, such as bias-adjustment, calculation of standardised precipitation indices and marine heatwave indicators require the processing of the full time series at a grid point at once: if the data is not stored in a way to facilitate this time-oriented reading, data processing can be prohibitively slow. In such cases, rechunking the dataset from its original structure (often in time-slices) to a time-oriented format is required. However, rechunking can also be both time- and storage-consuming and is not required in all cases. This switch can be used to control the approach to rechunking on an input-by-input basis. Two strategies are available: 1) `none`, where the imported primary variable objected is written to disk as a 'pickle', ready to be imported again by other parts of the processing chain. This option is most appropriate when dealing with large datasets that don't require rechunking: it has the disadvantage that the pickled object cannot be viewed with external tools, such as `ncview`. 2) `nc`, where the primary variable is rechunked to a NetCDF file. This option should be considered as the default and has the advantage of producing files that can be used with other tools, but can be space and time consuming. Must be one of: "none" or "nc".
- <a id="properties/checks"></a>**`checks`** *(string, required)*: Determine the degree of checking that should to be applied upon importing files. There are three elements to the checking procedure: 1). ensure that all dimensions except time match between input files (governed by the `join='exact'` and `compat='no_conflicts'` arguments to `xarray.open_mfdataset()`) 2) ensure that the time dimension is monotonic (governed by the `is_monotonic_increasing` property of an xarray time index and 3) ensure that there are no duplicated time variables (governed by the `has_duplicates` property of an xarray time index. For more information, please see documentation for these methods. The `all` argument applies all of these checks, while `none` applies none of them. While it may be tempting to ignore this step and disable all checks, it is recommended to set it to all, and investigate files that fail checks, before they propigate further into the processing chain, where they may cause unexpected problems. Must be one of: "all" or "none".
- <a id="properties/mergeFiles"></a>**`mergeFiles`** *(string, required)*: Should the set of input files be merged into composite files (e.g. merging years and/or experiments) (`TRUE) or should they each be handled as is (`FALSE`)? In cases where this parameter is set to `FALSE`, subsequent fields defining how merging should be structured are ignored.,. Must be one of: "TRUE" or "FALSE".
- <a id="properties/fieldSeparator"></a>**`fieldSeparator`** *(string, required)*: Character separating fields in the input file names, for use in merging files. Most often an underscore character '_'. Currently limited to a single character. Length must be between 0 and 1 (inclusive).
- <a id="properties/experimentField"></a>**`experimentField`** *(string, required)*: Number of the field in the filename to be used for merging files based on scenarios e.g. for the file `tas_AFR-22_NCC-NorESM1-M_rcp85_r1i1p1_CLMcom-KIT-CCLM5-0-15_v1_day_20360101-20401231.nc`, the fourth field (`rcp85`) contains the emissions scenario code, and this parameter would then be set to 4. If omitted, the experiment code is set to `noexp`. 1-based indexing is assumed. Must match pattern: `^\d*$` ([Test](https://regexr.com/?expression=%5E%5Cd%2A%24)). Default: `null`.
- <a id="properties/commonExperiment"></a>**`commonExperiment`** *(string or null, required)*: Many climate experiments, such as CMIP, involve splitting time into separate experiments e.g. a `historical` experiment that runs to 2005 and then the `rcp26` and `rcp85` scenario experiments that start from 2006. This field provides the name for the experiment that is common to all others (in this case `historical`) All (other) values of the `experimentField` will be merged with this experiment to produce one contiguous *dataseries*. Omission of this parameter will disable this feature, and all experiments will be processed individually. Default: `null`.
- <a id="properties/ensidFields"></a>**`ensidFields`** *(string or null, required)*: Comma-separated list of integers representing the fields to join together to make the *ensemble member identifier*, for use when merging files. Including the grid descriptor in this configuration is often a good idea, when the same model can be run on two different grids. If not specified, the ensemble member identifier will be set to `noensid`. 1-based indexing is assumed. Default: `null`.
